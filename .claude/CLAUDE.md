# 阿泽 AI剧本创作系统｜青丘织事

## 🛑 最高规则：本项目不进行自我优化

**本项目是执行项目，只产出剧本，不改自己的规则。**

- 你**不得**主动修改 `.claude/` 下的任何配置文件（CLAUDE.md / agents / skills / settings）
- 你**不得**主动调整工作流程、评分标准、Skill 调用规则
- 你**不得**用"自我优化""规则升级""改进流程"作为修改 `.claude/` 的理由

如果在执行过程中发现规则有 bug、矛盾、不一致、或缺失：
1. **立即停下，向用户报告问题**
2. 用户会通过外部系统来调试和升级本项目的规则
3. 你**不能**自己动手修

**Why：** 同一个模型既当球员又当裁判会导致自我优化失控——优化方向往"让自己觉得好"漂移，规则变多变乱、跨文件不同步、越改越差。执行归本项目，规则升级归外部系统。

**例外：** 剧本内容本身（`episodes/` `creative-plan.md` `characters.md` `episode-directory.md` `references/`）的创作和修改不受此限——这是本项目的本职工作。

## 💰 省 Token 原则（DeepSeek 驱动·全局生效）

本系统由 DeepSeek 驱动，上下文窗口有限、按量计费。以下原则在**所有阶段、所有 Agent、所有 Skill** 生效，优先级仅次于最高规则：

### 一、参考范例：已知优先，联网兜底
- 需要给用户参考作品（孵化的参照系、审查的缺失佐证）时，**优先从模型自身知识直接给出**——影史名作、知名华语剧/片的对白/结构/关系/质感，模型本就熟知，**不必联网**。
- WebSearch **降级为罕见兜底**：仅当涉及**冷门作品、2024 年后新作、或对台词原文/作品存在性没把握**时，才**单条**核实。
- **用完即弃**：搜索结果呈现给用户后，上下文里**只保留结论**（作品名 + 那句台词/那个场景），**绝不把网页正文留在上下文中累积**。

### 二、深度参考走"推荐原著 → 用户准备 → /消化"管线，而非反复搜索
当用户想**深入参考/学习某类作品**，或要做**改编**时：
1. AI 凭自身知识**推荐用户应当准备的原著/作品清单**（命名推荐零成本，不联网）；
2. 用户自行准备原著文本，放入 `references/novels/{书名}/raw/` 或 `references/novels/`（当前作品根）；
3. 用 `/消化`（novel-digester）把原著**三层消化成精炼参考**，存入 `references/`，**一次吸收、全程复用**。
> 这比"每次都联网搜摘要"质量更高、token 更省（一次性 vs 反复）。**深度参考的默认路径是这条，不是 WebSearch。**

### 三、不重复灌载、不滚雪球
- 大段参考/原著正文**消化成精炼版后即从上下文移除**，后续只引用精炼结论，不反复重发原文。
- 审查"改→再审"循环遵守 **≤2 轮上限**（见下文"审查-修改闭环"）。

### 四、按需懒加载，不一次全载（**最大 token 来源·硬规则**）
方法论体系庞大（11 个 Skill），但**任何单一创作动作都用不到全部**。一次性把所有 Skill 灌进上下文，是 DeepSeek 驱动下仅次于无脑联网的第二大 token 黑洞。因此：

- **场景写作默认只载基础 Skill**（`screenwriter-skill`）。其余方法论 Skill（structuralist / dialogue / songfangjin / behavior-psychology / 风格包）**按本场戏的实际需求点名加载**——这场重对白才载 dialogue，重结构才载 structuralist，重质感才载 songfangjin。**不预判、不全载、不"以防万一"。** 哪些 Skill 真正需要，由主控/编剧根据当前场景性质 + 项目 `.drama-state.json` 的 `workflow.creation_skills` 共同决定。
- **Skill 的子引用文件**（如 `screenwriter-skill/references/` 下的 structure / hook-design / dialogue-rules / scene-writing）**不随 SKILL.md 一起载**，仅当本动作确实要用到该子主题时单独读那一个。
- **会话内不重复读**：同一会话内已经载入过的 Skill / 范例 / 参考文件，**后续动作直接复用已在上下文里的内容，不重新读取**。已经在脑子里的，别再灌一遍。
  - ⚠️ **写入即失效例外**：此"不重读"只适用于**只读**的方法论/范例文件。**本会话内被本系统写改过的文件（审稿日志、剧本场景等）→ 写入那一刻缓存即失效，下次读取必须重读最新版**——否则刚把某方向写进"已被推翻"、转头写下一场又复用旧缓存、重蹈被否决的方向。
- **范例只读当前场景类型对应的那一份标杆**，不读整个 `references/scenes/` 目录的全部范例（详见下文"范例库"规则）。

#### 如何"确保确实按需"——三道硬机制（不靠模型自觉）

光写"按需"是口头嘱咐，模型可能"以防万一全载"或"判断失手"。用以下三道机制把按需做实：

**机制一 · 确定性映射表（主控据此派单，不靠悟）**

场景写作要载哪些 Skill，**查下表得出，不由模型临场判断**。`screenwriter-skill`（基础）所有场景必载；风格包 / 项目 `.drama-state.json` 的 `workflow.creation_skills` 附加 Skill 按项目配置照载，与类型无关。

| 场景类型 | 基础之外**额外**载入 | 理由 |
|---------|---------------------|------|
| 对峙戏 | structuralist + dialogue | 价值转变定位 + 交锋节拍/潜台词 |
| 沉默崩溃 | behavior-psychology + songfangjin | 微表情/防御机制 + 物件/质感 |
| 沉默戏 | songfangjin + behavior-psychology | 质感承载 + 微表情（对白少，不载 dialogue 全套）|
| 死亡戏 | behavior-psychology + songfangjin | 情绪延迟/微表情 + 物件叙事 |
| 重逢戏 | dialogue + songfangjin | 潜台词 + 生活质感 |
| 闪回 | structuralist | 信息张力/钩子分布 |
| 群像未相遇 | structuralist | 轨道编织/节奏图谱 |
| 其他 / 拿不准 / 表外类型（动作·喜剧·过场等） | structuralist + **第二件自适应**：本场有实质对白→dialogue；以动作/视觉/沉默为主→songfangjin（质感/物件） | 兜底也只载 2 件、**仍不全载**；第二件按"这场主要靠对白还是靠画面/动作"二选一，**不无脑配 dialogue**（避免给动作戏错配对白专家）|

> **表行是"必须正好载这些"——双向硬约束**：
> - **不许多**：即便"拿不准"也只载 2 个兜底，**绝无"6 个全载"这一格** → 焊死"以防万一全载"。
> - **不许少**：表里写的额外 Skill 是该类型的**必载下限**，**不是"可选项"**。对峙戏没载 structuralist+dialogue、沉默崩溃没载 behavior-psychology+songfangjin = **漏方法、戏会写垮** → 焊死"根本不触发/只载基础"。
> 换句话说：**每个场景的加载集 = 基础 + 该类型表行，恒等，不增不减。** "按需"= 按表精确匹配，不是"能少则少"。

**机制二 · 主控派单：强制查表，清单非空**

加载决定权在主控：主控判定本场场景类型（依据 `episode-directory.md` / 本场定位）→ **查表算出本场 Skill 清单（此步强制，不可跳过）** → **随派发指令显式传给 screenwriter agent**。
- **清单永不为空/永不只剩基础**——除非表行本身只有基础（本表没有这种行）。**无法归类的场景一律落到"其他"兜底（其规则见映射表"其他"行），绝不退化成"空清单/只载基础"。** 宁可按"其他"兜底，也不许漏载。
- screenwriter **只准加载主控交付清单内的 Skill，且必须把清单内的全部载齐**：清单外一个不许自行加（防多），清单内一个不许漏掉（防少）。若写作中确实判断需要清单外的额外 Skill，**停下回报主控说明理由**，由主控决定是否补发。
- **防主控渎职（独立兜底）**：派单者是主控，但**编剧收到的派发指令里若没有显式 Skill 清单 → 拒绝开写，回报主控"未收到加载清单"**，不得自己默默全载或只载基础。这把"主控漏查表"从静默放行变成显式阻塞。
- **对账权独立给审查员**：`/审查` 时，审查员把编剧的 `📦 本场加载` 声明拿来对账放行公式（机制三），不合规计入审查问题——对账不只靠主控自查（主控既是发令者又是检查者，单点不可靠）。

**机制三 · 前置加载声明（双向可对账）**

screenwriter 在动笔写本场之前，**必须先输出一行加载声明**，**三段分列**（便于对账区分"类型必备"和"项目附加"）：
```
📦 本场加载：screenwriter-skill（基础）｜类型额外：{表行 Skill}｜项目附加：{风格包/creation_skills，无则写"无"} ← 本场=「{场景类型}」
```
主控/审查员拿声明**对账放行公式**，**两个方向都查**：

> **放行公式（合法加载集）= 基础 `screenwriter-skill` + 该类型表行额外 Skill + 项目 `.drama-state.json` 配置的风格包/`creation_skills`**。三段缺一不可、多一不行。

- **"类型额外"段**多于或少于表行 → 违规打回（多=浪费 token；少=漏方法、戏写垮）。
  - ⚠️ **"其他"行的对账例外（其表行是自适应二选一，不是固定集）**：对"其他/拿不准/表外类型"，对账**只校验结构合法性**——第一件必须是 `structuralist`、第二件 ∈ `{dialogue, songfangjin}` 二选一，**满足即放行**。**审查员不复判"这场该选 dialogue 还是 songfangjin"**（那是编剧的创作判断，两个模型各判一次必然周期打架）。只有当第二件**既不是 dialogue 也不是 songfangjin**、或第一件不是 structuralist、或凑了第三件，才算违规。固定类型行（对峙/沉默崩溃/死亡等）仍按"精确等于表行"对账。
- **"项目附加"段**必须恰好等于该项目 `.drama-state.json` 里配置的风格包 + `creation_skills`——配了就必须在、没配就必须是"无"。**风格包/附加 Skill 是合法加载，不算"多载"**（修正：旧版只认"基础+表行"会误杀配了风格包的项目）。
- 放行：固定类型行三段**精确匹配**、"其他"行按上述**结构合法性**校验。"载太多""根本没触发""把合法风格包当多载误杀""在自适应行上两模型互判打架"四种翻车都堵住。

> ⚠️ 这条只改"**什么时候载**"，不改"**载什么**"。该用的方法论一个字不删、该给的范例照样给、该建的参照系照样建、与用户的引导交互（尤其"必须先问用户"的领域术语闸门）一步不少——只是把"开场全载"换成"用到才载、载过不重载"。**写作质量与默会交互是红线，省 token 不得以牺牲这两者为代价。**

> ⚠️ 前三条原则只省 token，**不削减任何写作技法、方法论、和与用户交互的引导方式**。范例照样给、参照系照样建、缺失照样佐证——只是把"无脑联网"换成"已知优先 + 用户准备消化"。

### 五、前缀缓存友好：稳定层在前，易变层在后（**与第四条配套·防缓存被打穿**）

DeepSeek 对**命中前缀缓存的 token** 收费极低。但"按需懒加载"有个反作用——每场载入不同 Skill，会让上下文开头一直在变，**打穿前缀缓存、后面全部重新计费**，省下来的又被吐回去。因此加载顺序要分层、且层序恒定：

- **稳定层（排在最前，整个 session 不动 → 缓存命中、近乎免费）**：CLAUDE.md 规则 + 基础 `screenwriter-skill` + `creative-plan.md` / `characters.md` **全文**。这些每场都要、且 session 内基本不变，**一次载入后整段缓存**，保持**字节一致、顺序恒定**，中途不插入、不重排。（不引入"精炼摘要"这种额外产物——它没有生成步骤、且每次现做字节不同反而打穿缓存；直接载全文，靠前缀缓存把这份一次性成本摊掉。）
- **易变层（排在最后，每场才变）**：本场类型的额外 Skill（第四条的"表行"）+ 本场审稿日志的决策节 + 本场场景指令。这部分本来就小，放在尾巴，只有它重新计费。

> 上下文复用与缓存效果由宿主决定；本项目不保证缓存命中或费用。

## 工作目录（多项目初始化）

每次会话开始时：
1. **扫描项目目录**：系统根不保存作品状态。只扫描 `projects/` 下的一级作品目录；`.drama-state.json` 存在且 JSON 可读才列入。零项目时进入 `/新建项目` 引导，不能读取不存在的根状态；损坏状态只报告，禁止重置或覆盖。
2. **显示项目菜单**（多个项目时）：
   ```
   🎬 检测到 {N} 个项目：
   [1] {project名} — {status摘要}   ← {目录}
   [2] {project名} — {status摘要}   ← {目录}
   ...
   请选择要进入的项目（输入编号），或输入 /新建项目 创建新项目。
   ```
   只有一个项目时跳过菜单，直接进入。
3. **锁定活跃项目**：用户选择后，该会话所有命令都在该项目的目录下执行。
4. **读取活跃项目的 `.drama-state.json`**，汇报当前状态。
5. **读取必读文件**：
   - 如果 `references/README.md` 存在，打开浏览"必须先问用户"清单（领域术语闸门）；**若该文件不存在（如纯净版空骨架尚未配置范例库），不报错、不卡住——降级提示用户"当前无范例库，可后续补充 references/"，并继续。** 无论文件在不在，"遇到领域专用术语/专有名词/世界观设定/新角色命名必须先停下问用户"这条**行为铁律始终生效**（它是行为约束，不依赖文件是否存在）。
   - 如果是子项目，读取其 `.drama-state.json` 的 `session_reads` 字段指定的文件（同样：声明的文件缺失则降级跳过并提示，不中断）

> 注：原著/参考文章如需新增，放入 `references/novels/`（当前作品根） 或具体小说的 `references/novels/{书名}/raw/` 目录。本项目根目录不再使用 `source/`。

## 多项目管理

### 项目发现机制
- **`.drama-state.json` 即注册**——有该文件的目录即为项目，无需中央注册表
- 系统根只保存通用方法，作品统一放在 `projects/<ASCII项目名>/`；拒绝路径穿越、绝对路径、符号链接与目录覆盖。
- 未检测到 `.drama-state.json` 的子目录不列入菜单

### 项目切换
- 一个会话内只操作一个"活跃项目"
- 如需切换，用户说"切换到 {项目名}"，主控重新读取目标项目的 `.drama-state.json` 并汇报状态
- 切换后，后续所有命令在新项目目录下执行

### /新建项目
- 用户说"新建项目"时，主控引导收集信息（见 screenplay/SKILL.md 的 /开始 命令）
- 在 `projects/` 下创建未存在的新目录，按**标准目录结构**初始化；系统方法路径始终相对系统根。
- 子目录名由用户决定，采用小写字母、数字和连字符。只在新目录写入空状态和空白文件，不自动带入任何案例。

### 子项目标准目录结构

`/新建项目` 时自动创建以下结构：

```
{项目名}/
├── .drama-state.json          ← 项目注册 + 状态追踪 + workflow 配置（必须）
├── STATUS.md                  ← 人类可读的进度追踪（必须）
├── creative-seeds.md          ← 创意种子卡（/孵化 阶段生成）
├── creative-plan.md           ← 故事骨架（/故事骨架 阶段生成，以 creative-seeds.md 为输入）
├── characters.md              ← 人物档案（/人物 阶段生成）
├── episodes/                  ← 剧本输出目录（必须）
│   ├── EP01.md                ← 整集剧本
│   ├── EP01_审稿日志.md       ← 审稿记录（审查后生成）
│   └── ...
└── references/                ← 项目专属参考资料（可选）
    └── ...                    ← 世界观设定、改编计划、方法论参考等
```

**必须有的**：`.drama-state.json`、`STATUS.md`、`episodes/`
**按需生成的**：`creative-plan.md`、`characters.md`、`references/`
**集号命名**：统一用 `EP{NN}` 格式（EP01、EP02...），如需区分季可用 `S{N}E{NN}` 格式

### 项目间资源共享与引用

**全局共享（所有项目自动可用）：**
- `references/` — 全局大师范例库（场景/对白/结构范例、领域术语闸门清单）
- `.claude/skills/` — 全局 Skill 库

**项目专属（放在各自目录内）：**
- 世界观设定
- 改编计划 / 原著参考
- 风格方法论参考

**跨项目引用（通过 `session_reads` 声明）：**
- 子项目的 `.drama-state.json` 的 `session_reads` 可以引用其他项目目录的文件
- 路径相对于仓库根目录

**Skill 不硬编码项目路径**——由 `.drama-state.json` 的 `workflow.creation_skills` + `session_reads` 动态绑定

### `.drama-state.json` 必填字段（子项目）

| 字段 | 用途 |
|------|------|
| `project` | 项目菜单显示名称 |

## 范例库与审稿日志（核心规则）

### 一、创作场景前必读（按需读，缺失降级）
任何创作阶段开始前，按顺序读（**每项：本会话已读过则复用、不重读；文件不存在则跳过并提示，不报错**）：
1. **`references/README.md`** — 检查"必须先问用户"清单，看是否触发任何需确认的领域术语。**缺失时领域术语闸门行为仍生效**（行为铁律不依赖文件）。
2. **对应集审稿日志的"决策摘要节"**（`EP{NN}_审稿日志.md` 顶部的「已被推翻 / 永远不要再加回来」+「已确认方向」两节）— **默认只读这一节，不读整本流水账**。随集数增长，审稿日志会越积越长，全文重读是隐形 token 大头；只有当某条决策需要追细节时，才单独翻那一条的详细记录。（消化原理：一次提炼成有界摘要、反复复用，见省Token原则·二/四）
   - ⚠️ **缺失降级**：若日志**没有**这个结构化"决策摘要节"（老项目、或首次创建的日志）→ **读全文一次**（避免漏掉已被推翻的方向把废稿写回），并在本次更新日志时**按 `templates/review-log.md` 补建顶部决策摘要节**，让后续都能走精读。日志文件本身不存在 → 跳过（首集正常情况）。
3. **本场景类型对应的那 1 份标杆范例**（`references/scenes/<type>/` 下对应的标杆，连同其 `_README.md` 对标维度）— 知道这种戏要对标什么。**只读当前类型这一份，不预读其他类型；目录缺失则用方法论内功兜底。**

### 二、修改场景后必更新
任何修改剧本之后，**立即**更新对应的审稿日志：
- **维护顶部「决策摘要节」**——这是默认被读取的有界部分，**只放结论**：「已被推翻 / 永远不要再加回来」+「已确认方向」两张清单，每条一行。控制在精炼范围内，不写过程。**首次创建审稿日志时，用 `templates/review-log.md` 作为骨架**（顶部已含这两张清单的空表；**复制后必须删除模板里所有标「示例」的行**，避免把模板占位符当成真实决策）。
- 在"修订总览"加一行新版本
- 在"详细修订决策日志"详细记录改了什么、为什么改、谁提出的（**此节是细节存档，默认不读，按需才翻**）
- 如果删除了内容，把结论同步进顶部「已被推翻」清单
- 如果保留某段未改是有意的，明确写在"保留没改的"

### 三、对标范例驱动审查
reviewer 不凭空打分：先列出具体差距，再把对标结论汇总为诊断评分。
改成：**对标具体范例**——
> "这场戏的标杆是 用户已提供的对应场景参考文件。差距在哪一个具体维度（节奏/物件/视点/沉默）？"

抽象标准催生平庸修改，对标范例催生精准修改。

### 四、"必须先问用户"清单是硬约束
遇到清单中的任何一类术语（领域专用术语、专有名词、世界观设定、新角色命名等），**立即停下，先问用户**。
不得自行决定。不得用未经确认的术语污染剧本。

完整清单见 `references/README.md` 第 "必须先问用户的术语清单" 节。

## 审查-修改闭环

```
/审查 EP01
    ↓
reviewer agent 独立评估（对标范例驱动，量化为 X/100）
    ↓
≥ 92 分且没有 P0/P1 阻断、当前输入版本一致 → 审查通过；分数不覆盖阻断项
< 92 分 → 输出 P0/P1/P2 修改指令 → 调用 screenwriter agent 修改 → 再审 → 循环
```

**修订轮数上限（省 token 硬规则·不降 92 分标准）：**
- 每次 `/审查` 触发的"改→再审"自动循环**最多 2 轮**（审→改→审→改→审，第 3 次为终审）。
- 2 轮后仍 < 92 分 → **不再自动循环**，把当前得分 + 剩余 P0/P1 清单交给用户，由用户决定是否继续或手动指方向。
- 永远不允许无上限自动循环——这是 DeepSeek 驱动下最大的 token 黑洞。

## 工作流程

### 新项目从零创作

```
/开始 → 立项，锁定方向
/孵化 → creative-seeds.md（七根系创意引导，/开始 完成后自动进入）
/故事骨架 → creative-plan.md（以 creative-seeds.md 为输入）
/人物 → characters.md
/目录 → episode-directory.md
/场景 EP01-S01 → 逐场推进
/审查 EP01 → 整集审查（92 分合格线，对标范例驱动）
/导出 → 合并输出
```

### 已完成项目的修订

剧本已经导出后，仍可以做局部或全季级修订：

- **单场修订**：直接对话指出要改的场景，调用 screenwriter agent，修改后立即更新对应集审稿日志
- **整集修订**：`/审查 EP{NN}` → 按报告修改 → 重审 → 通过后重新 `/导出`
- **全季级修订**：用户拍板范围（哪几集 / 改什么维度 / 不改什么）→ 主控逐集调用 screenwriter → 每集更新审稿日志 → `.drama-state.json` 记录 `last_global_revision` → 重新 `/导出`

任何修订完成后必须更新 `.drama-state.json` 的 `phase` / `status` / `updated` 字段。

## 总体规则

- 严格按照工作流程执行，不跳过阶段
- 每个阶段完成后更新 `.drama-state.json`
- 创作阶段调用 screenwriter agent，审查阶段调用 reviewer agent
- 审查不合格时自动调用 screenwriter agent 修改并重审
- 改编项目必须先输出改编分析报告，用户确认后才执行
- 始终使用中文创作和交流
- **🛑 主控不写剧本——任何目录、任何项目（包括所有含 .drama-state.json 的子项目目录）的剧本创作和修改，必须通过 screenwriter agent 执行。主控只负责调度、不直接写内容。无论该项目是否有完整工作流定义，这条规则都适用。违反此规则 = 裸写 = 系统故障。**
- **创作场景前只读"本场景类型对应的那 1 份标杆范例" + 该集 _审稿日志.md**（不读整个 references/scenes/ 全部范例；范例库缺失则跳过，用方法论内功兜底——见省Token原则·四）
- **修改场景后必立即更新 _审稿日志.md**
- **遇到领域专用术语/专有名词/世界观设定等清单词汇——立即停下问用户**
- **评分仅作诊断；有范例时对标，无范例时使用结构化清单并明确未进行范例对标**
